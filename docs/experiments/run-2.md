## Fixes after this run

All applied on the branch `fix/second-run-findings`. Where the result differs from the proposal:

- Fix 1 looks for a numbered list followed by a question, with no word list per language.
- Fix 3 reports the missing ticket commit as `[skip]` with the command to run first, and the plan now says what a `[skip]` can mean.
- Fix 4 also reached `templates/AGENTS.md`, the close-change skill, `docs/guide.md` and `README.md`, which all showed `/implement <change>`. A named ticket whose blocker still has open boxes now stops and names the blocker's command.
- Fix 10 puts the guardrails in step 5 of the plan, before the last build ticket's check. Step 6 is the manual test and step 7 the close. When the next ticket is the manual test, `check implement` fails for each hook that has not fired in any `/implement` session.

Each fix names the kit document it went into:

1. **Checker, approval question** (row 3): in `scripts/experiment/checks.mjs`, the `to-tickets` approval check must not depend on the conversation language. Accept the Spanish label too (`/blocked by|bloquead[oa]s? por/i`), or better, look for the numbered ticket list followed by a question.
2. **Checker, early stop** (row 5): when `check close` sees a correct early stop, add a line saying the run is not finished and naming the next frontier ticket, so eight `[ok]` lines are not read as a finished close.
3. **Checker, implement before any ticket** (row 3): when no commit carries `Refs: <change>#N` yet, report "no ticket implemented yet" instead of a failure.
4. **Ticket references in the next-step messages** (rows 4 and 5): the run first stopped after ticket 1 because typing the same `/implement remove-todo` five times made it unclear whether the change was done, and ticket 4 still pointed to `/implement remove-todo` for ticket 5. The adapter already accepts `<change>#N`, but every next-step message shows only `<change>`. In `templates/docs/agents/issue-tracker.md`, **When a skill says "publish the tickets"**, step 6: end with one command per ticket (`/implement <change>#1`, `/implement <change>#2`, ...), each in a fresh session, and say that `/implement <change>` alone takes the next unblocked ticket. In **When a skill says "fetch the relevant ticket"**: when a ticket is done, name the exact next command (`/implement <change>#N`, or `/close-change <change>` when every box is ticked). An explicit `<change>#N` does not check that the ticket is unblocked; say what to do when it is not.
5. **The plan, section 4**: in `docs/experiment-log.md`, use `/implement remove-todo#N`, with N taken from the last `check implement`.
6. **Checker, next ticket**: `check implement` prints the command to run next (`next: /implement remove-todo#2`), not only the ticket's title.
7. **Review headings** (row 4, tickets 2 to 4): in `templates/docs/agents/issue-tracker.md`, **While working on a ticket**, say that the final message shows the code-review reports under the literal headings `## Standards` and `## Spec`, untranslated whatever the conversation language, and not folded into the ticket summary. In `scripts/experiment/checks.mjs`, look for those two headings instead of the bare words, so the check fails on a missing heading and not on the language.
8. **Manual test steps** (row 4, manual test): in `templates/docs/agents/issue-tracker.md`, **Ticket format**, say that the manual test ticket's boxes run as one sequence from a fresh to-do file, so each expected result must follow from the state the earlier boxes leave, or a box must say its own starting state. In **When a skill says "fetch the relevant ticket"**, the manual test paragraph: before listing the steps, check each expected result against the spec and the steps before it, and add a `- Note:` when one cannot happen. Then ask the user what they saw at each step instead of a yes/no list, and compare it with the expected result before ticking.
9. **Checker, its own output in the transcript** (rows 4 and manual test): the `!` output of a check lands in the conversation, Claude answers it, and the transcript segment the next check reads then includes that answer. After the failed checks of tickets 2, 3 and 5, Claude redid the review report or the question, so a second check would have passed on the same commit. In `scripts/experiment/transcript.mjs`, end a segment at the first `experiment.mjs check` input.

In `docs/experiment-log.md`, make it a numbered step of its own, done in the session of the last build ticket before the manual test, and have `check implement` warn when the next ticket is the manual test and a hook from the three has not fired yet.
11. **Quality gate output** (row 4, guardrails): in `hooks/quality-gate.mjs`, the block message keeps only the last 4000 characters of the check's output, so it can start mid-word and drop an early failure. Keep the start and the end of the output, with a marker where it was cut, so both the first failures and the summary show.
